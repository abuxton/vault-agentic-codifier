# Codification: Auth Mounts

## 1. Purpose

Generate `vault_auth_backend` and the method-specific resources (config, roles,
groups, users) for every auth mount discovered in every namespace, so that
`terraform plan` after import shows no change.

Input: `discovered_terraform/raw/<namespace>/auth_mounts.json` and per-mount
role/config payloads.
Output: one file per namespace and mount, for example
`namespaces/admin_platform/auth_approle.tf`, plus `imports.tf` per layer and
`auth-mounts/coverage.md`.

## 2. Governance

- **Ownership**: this skill owns `vault_auth_backend` and every auth role,
  config, group and user resource. The only exception is a top-level OIDC/LDAP
  mount in the `admin` namespace, which belongs to `codification-admin-config`.
- **NEVER emit `role_id` or `secret_id`** (including `secret_id_accessor`
  values). Role IDs are server-generated and are not configuration.
- **NEVER emit `vault_identity_*`**; those belong to `codification-teams`.
- **Secret guard**: `client_secret`, `oidc_client_secret`, `bindpass`,
  `secret_key` and similar become `variable "<label>_<field>" { sensitive = true }`
  with no default.
- The `token/` mount is never emitted.
- Layer: root and `admin` mounts -> `admin/`; tenant mounts -> `seed/`.
- All shared coding standards apply (section 6).

## 3. Prerequisites

1. `auth_mounts.json` exists per namespace (from `sys/auth`, with `accessor`,
   `config`, `options`, `local`).
2. Policy labels from `codification-policies` are available (the policy set per
   namespace) so `token_policies` can be cross-referenced.
3. Naming library and provider template available.

## 4. Process

For each namespace, for each mount (skip `token/`):

1. **`vault_auth_backend`**: `type`, `path` (trailing `/` stripped),
   `description` when non-empty, `local` only when `true`, and a `tune {}`
   block with `default_lease_ttl`, `max_lease_ttl`, etc. Zero values are omitted.
2. **Method-specific resources** by `type`:
   - `approle` -> `vault_approle_auth_backend_role` per role.
   - `oidc` / `jwt` -> `vault_jwt_auth_backend`, `vault_jwt_auth_backend_role`;
     `oidc_client_secret` -> sensitive variable.
   - `ldap` -> `vault_ldap_auth_backend`, `vault_ldap_auth_backend_group`,
     `vault_ldap_auth_backend_user`; `bindpass` -> sensitive variable.
   - `kubernetes` -> `vault_kubernetes_auth_backend_config`,
     `vault_kubernetes_auth_backend_role`.
   - `aws` -> `vault_aws_auth_backend_client`, `vault_aws_auth_backend_role`;
     `secret_key` -> sensitive variable.
   - `cert` -> `vault_cert_auth_backend_role`.
   - Unknown type -> `vault_auth_backend` plus a documented
     `vault_generic_endpoint` fallback; list it in `coverage.md`.
3. **Policy cross-reference**: for each `token_policies` entry that exists as a
   `vault_policy` in the same namespace, emit
   `vault_policy.<label>.name`; otherwise emit the literal string and add a
   warning to `coverage.md`.
4. **Role/backend linkage**: `backend = vault_auth_backend.<label>.path`.
5. **Import blocks**: backend `id = "auth/<path>"`; role
   `id = "auth/<path>/role/<name>"`. Namespace-qualified form follows TASK-006.
6. **Coverage**: `auth-mounts/coverage.md` lists every mount with resource type,
   fallback or "unsupported", and any warnings.
7. Provenance header (`Capability: auth-mounts`), fmt, validate.

## 5. Example HCL: approle in `admin/platform`

`namespaces/admin_platform/auth_approle.tf`

```hcl
# Generated by vault-brownfield-codifier
# Capability: auth-mounts
# Doc ref: https://developer.hashicorp.com/vault/docs

resource "vault_auth_backend" "admin_platform_approle" {
  provider    = vault.platform
  type        = "approle"
  path        = "approle"
  description = "AppRole auth - platform namespace"
}

resource "vault_approle_auth_backend_role" "admin_platform_approle_platform_ci" {
  provider           = vault.platform
  backend            = vault_auth_backend.admin_platform_approle.path
  role_name          = "platform-ci"
  token_policies     = [vault_policy.admin_platform_platform_devops_write.name]
  token_ttl          = 3600
  token_max_ttl      = 14400
  secret_id_num_uses = 1
  secret_id_ttl      = 1800
}
```

Imports:

```hcl
import {
  to = vault_auth_backend.admin_platform_approle
  id = "auth/approle"
}

import {
  to = vault_approle_auth_backend_role.admin_platform_approle_platform_ci
  id = "auth/approle/role/platform-ci"
}
```

### Integer-seconds TTL note

`secret_id_ttl`, `token_ttl` and `token_max_ttl` on
`vault_approle_auth_backend_role` are **integers in seconds**. Do not emit
duration strings (`"30m"`, `"1800s"`); this was a known gotcha in project
history. The harness comments (`# 30 minutes in seconds`) show the value, not a
string. The `tune {}` block on `vault_auth_backend` is the exception: it takes
duration strings, so convert `default_lease_ttl_seconds` accordingly or omit
when zero.

## 6. Coding standards applied

1. Provenance header on every `.tf` file.
2. Provider pin `hashicorp/vault ~> 4`, `>= "1.9"`, `skip_child_token = true`.
3. Labels from `<namespace>/<path>/<name>`, `/` and `-` -> `_`; `r_` prefix for
   digits.
4. One namespace targeting style per run; never mixed.
5. Secret guard (section 2); no `role_id`, no `secret_id`.
6. Ownership: auth resources only.
7. Every backend and role has an `import {}` block.
8. Zero TTL values are omitted (not emitted as `0`).
9. Same-namespace policies referenced as `vault_policy.<label>.name`.
10. No mounts in a namespace -> no file.
11. `terraform fmt -check -recursive` and `terraform validate` pass.

All TTL values are integer seconds unless the provider argument is a duration
string (`tune {}`), in which case the generator converts and documents it.

## 7. Acceptance criteria (harness)

- 5 `vault_auth_backend` resources, all `type = "approle"`, `path = "approle"`:
  root, `admin`, `admin/platform`, `admin/app-billing`, `admin/app-identity`;
  `token/` not emitted.
- 5 `vault_approle_auth_backend_role`: `terraform-admin` (root),
  `namespace-provisioner` (`admin`), `platform-ci`, `billing-service`,
  `identity-service`.
- Each role: `token_ttl = 3600`, `token_max_ttl = 14400`,
  `secret_id_num_uses = 1`; `secret_id_ttl` = 900, 900, 1800, 900, 900
  respectively (integers).
- `grep -rE 'role_id|secret_id\s*=' discovered_terraform/terraform` returns 0
  (the attribute names `secret_id_ttl` and `secret_id_num_uses` excluded).
- `coverage.md` lists 5 mounts and 5 roles, none "unsupported".
- With `userpass` enabled in `admin/app-billing`, a fallback is emitted and
  documented.
- 10 `import {}` blocks; fmt and validate pass.

## 8. Stop conditions

- A payload contains a credential in a field that would be emitted: stop and
  report the field name, not the value.
- A role references a mount not in `auth_mounts.json`.
- Label collision within a layer.
- Mount type unknown **and** no fallback payload is available to document.
