# Codification: Policies

## 1. Purpose

Generate one `vault_policy` per ACL policy in every discovered namespace and
produce a correlation matrix that shows which auth roles, identity groups and
identity entities reference each policy. The matrix is also emitted as JSON so
`codification-teams` can consume it.

Input: `discovered_terraform/raw/<namespace>/policies.json` (plus
`auth_mounts.json` and `identity.json` for correlation, read-only).
Output: `discovered_terraform/terraform/<layer>/policies.tf`, `imports.tf`,
`policies/<namespace>/<name>.hcl`, `policies/correlation.md`,
`policies/correlation.json`, `policies/coverage.md`.

## 2. Governance

- **Ownership**: only `vault_policy` is emitted. No auth backend, role, mount,
  namespace or identity resources.
- Policies are placed in the layer matching their namespace: root -> `admin/`,
  `admin` -> `admin/`, tenant namespaces -> `seed/`.
- Policy bodies are copied verbatim. Namespace-relative `path` stanzas (for
  example `secret/data/platform/sre/*`) are never rewritten.
- Correlation is read-only analysis: no policy is fabricated for a dangling
  reference.
- All shared coding standards apply (section 6).

## 3. Prerequisites

1. `policies.json` exists for every namespace listed in `namespaces.json`.
2. `auth_mounts.json` and `identity.json` exist for correlation (missing ->
   mark the affected column "unavailable", do not fail).
3. Naming library and provider template available.
4. `/opt/homebrew/bin/terraform` available.

## 4. Process

1. **Load** each namespace's `policies.json` (`name`, `policy` text).
2. **Skip** `default` and `root`.
3. **Choose body style by line count** of the policy text:
   - More than 10 lines: write `policies/<namespace>/<name>.hcl` (namespace with
     `/` normalised to `_`) and emit
     `policy = file("${path.module}/policies/<namespace>/<name>.hcl")`.
   - 10 lines or fewer: emit a heredoc `policy = <<-EOT ... EOT`.
4. **Generate** `vault_policy` with `name` and `policy`; apply the namespace
   targeting style chosen for the run.
5. **Import blocks** per policy (section 5).
6. **Correlate**: for each policy, find (a) auth roles whose `token_policies` /
   `policies` list it, (b) identity groups and (c) entities that list it. A
   reference to a policy not in the same namespace's set is `dangling` and is
   marked as such. Write `correlation.md` (policy x auth role, identity group,
   entity, per namespace) and `correlation.json`.
7. **Coverage**: `coverage.md` lists EGP/RGP objects discovered
   (`sys/policies/egp`, `sys/policies/rgp`) with the resource used per TASK-006
   (dedicated resource or `vault_generic_endpoint`); "none discovered" if empty.
8. Prepend provenance header (`Capability: policies`); run fmt and validate.

## 5. Example and import ID format

Root-namespace `operator` policy (more than 10 lines, so file-backed):

```hcl
# Generated by vault-brownfield-codifier
# Capability: policies
# Doc ref: https://developer.hashicorp.com/vault/docs

resource "vault_policy" "operator" {
  name   = "operator"
  policy = file("${path.module}/policies/root/operator.hcl")
}
```

A short policy (10 lines or fewer) in `admin/platform`:

```hcl
resource "vault_policy" "admin_platform_platform_sre_read" {
  provider = vault.platform
  name     = "platform-sre-read"
  policy   = <<-EOT
    path "secret/data/platform/sre/*" {
      capabilities = ["read", "list"]
    }
  EOT
}
```

### Namespace-qualified import ID (TASK-006 resolution)

TASK-006 verifies import IDs against the harness; this skill uses its table
rather than inferring. The convention: the `import` `id` is the policy name for
the namespace the provider is configured for; the provider prefixes the
namespace through its provider-level or resource-level `namespace` setting.

| Namespace | Style | Import `id` |
|---|---|---|
| root | any | `operator` |
| `admin` | alias or `namespace` argument | `admin` / `namespace-admin` |
| `admin` | when TASK-006 reports the `<ns>/<name>` form is required | `admin/namespace-admin` |

If the verified TASK-006 format is `<namespace>/<name>` for non-root, emit
`admin/operator`-style IDs consistently; if it is name-only, emit `operator`.
Never mix both in one run. Record the chosen form in `coverage.md` header.

## 6. Coding standards applied

1. Provenance header on every `.tf`; `.hcl` policy files are verbatim bodies
   without a header.
2. Provider pin `hashicorp/vault ~> 4`, `>= "1.9"`, `skip_child_token = true`.
3. Labels from `<namespace>/<path>/<name>` with `/` and `-` -> `_`;
   `r_` prefix when digit-leading.
4. One namespace targeting style per run (alias or `namespace` argument).
5. Secret guard: policy text is reviewed for embedded secrets; none expected.
6. Ownership: `vault_policy` only.
7. `import {}` for every policy in the layer's `imports.tf`.
8. Zero-TTL omission: not applicable.
9. Cross-references: correlation outputs use labels; `vault_policy.<label>.name`
   is the reference form other skills use.
10. Empty set: namespace with no non-builtin policies emits no `policies.tf`.
11. `terraform fmt -check -recursive` and `terraform validate` pass.

## 7. Acceptance criteria (harness)

- 9 `vault_policy` resources: root `operator`; `admin` -> `admin`,
  `namespace-admin`; `admin/platform` -> `platform-sre-read`,
  `platform-devops-write`; `admin/app-billing` -> `billing-developers-read`,
  `billing-owners-write`; `admin/app-identity` -> `identity-developers-read`,
  `identity-owners-write`. `default` and `root` not emitted.
- Distribution: 3 in `admin/` (operator, admin, namespace-admin), 6 in `seed/`.
- Lossless round-trip: the policy text from Vault equals the text rendered from
  the generated file (whitespace-normalised); `terraform plan` shows no change.
- `correlation.md` records `operator` <- `terraform-admin`,
  `namespace-admin` <- `namespace-provisioner` and the three
  `vault-*-admin` groups, `platform-devops-write` <- `platform-ci`,
  `billing-developers-read` <- `billing-service`,
  `identity-developers-read` <- `identity-service`.
- A policy named by a role but absent from its namespace is marked `dangling`.
- `correlation.json` validates as JSON and is non-empty.
- 9 `import {}` blocks.

## 8. Stop conditions

- A `policies.json` is unreadable or lacks `policy` text for a listed name.
- Two policies in one layer normalise to the same label.
- TASK-006 import ID table is unavailable and the format cannot be determined:
  stop and ask rather than guess.
- A policy name contains characters that cannot form a safe file name.
