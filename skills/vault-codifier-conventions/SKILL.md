# Vault codifier: shared conventions

Every `discovery-*` and `codification-*` skill refers to this file instead of
carrying its own copy. If a rule here conflicts with a skill, this file wins.

## 2. Hard rules

1. **Read-only.** Only `GET` and `LIST`. Use the `exporter` token from
   `vault-exporter-setup`, never a root or operator token.
2. **Never emit** these resource types: `vault_kv_secret_v2`, `vault_kv_secret`,
   `vault_generic_secret`, `vault_approle_auth_backend_role_secret_id`. They
   persist secret material in state.
3. **Builtin objects are never codified.** Policies `default`, `root` and `default-ceiling` (Vault 2.x, every namespace); auth
   mount `token/`; secrets mounts `sys/`, `identity/`, `cubbyhole/`.
4. **Ownership.** One resource type has exactly one owning skill:

   | Resource type | Owner |
   |---|---|
   | `vault_namespace` | `codification-namespaces` |
   | `vault_policy`, `vault_egp_policy`, `vault_rgp_policy` | `codification-policies` |
   | `vault_auth_backend` and auth roles/config | `codification-auth-mounts` (top-level OIDC/LDAP in `admin`: `codification-admin-config`) |
   | `vault_mount` and engine config | `codification-secrets-engines` |
   | `vault_identity_*` | `codification-teams` |
   | `vault_audit`, `vault_quota_*`, system `vault_generic_endpoint` | `codification-root-config` |

   Other skills reference the owner's resources by address and never
   re-declare them.
5. **No import for `vault_generic_endpoint`.** The provider does not support it.
   Do not emit an `import {}` block; list it in the README as adopted by apply.

## 3. Secret guard

Before any value from a raw payload is written to a `.tf`, `.hcl`, `.md` or
`.json` file, check its key.

Replace the value with a sensitive variable reference `var.<field>` and add a
warning to the run report when the key is any of:

`secret_id`, `role_id` (only when auto-generated), `bindpass`, `client_secret`,
`oidc_client_secret`, `token`, `root_token`, `client_token`, `password`,
`connection_url` (may embed a password), `secret_key`, `access_key` (only when
secret), `credentials`, `private_key`, `license`, `license_text`, `data` (KV).

Or when the key starts with `secret_`, `password_` or `token_value`, or the
value starts with `SYNTHETIC-`.

Declare each variable `sensitive = true` with no default. Never log the value:
report only the field name and the file.

Final check after generation. Both commands must print nothing:

```bash
grep -rn "SYNTHETIC-" discovered_terraform/terraform
grep -rnE '(secret_id|bindpass|client_secret|private_key)\s*=\s*"[^"]' discovered_terraform/terraform
```

`discovered_terraform/raw/` is git-ignored because raw payloads can hold
tokens. Treat it as sensitive.

## 4. Provenance header

Every generated `.tf` and `.hcl` file starts with:

```hcl
# Generated by vault-brownfield-codifier
# Capability: <slug>
# Doc ref: <public https URL from the Terraform MCP lookup or the Vault docs>
# Namespace: <full path, or (root)>
```

The slug is one of `namespaces`, `root-config`, `policies`, `auth-mounts`,
`secrets-engines`, `teams`, `admin-config`. Do not write timestamps: output
must be byte-identical across runs (CAC5). Policy `.hcl` files that must match
Vault byte-for-byte are the exception and carry no header.

## 9. Validation

After generating a layer:

```bash
terraform -chdir=discovered_terraform/terraform/<layer> fmt -check -recursive
terraform -chdir=discovered_terraform/terraform/<layer> init -backend=false
terraform -chdir=discovered_terraform/terraform/<layer> validate
```

All three must exit 0. Zero-diff import checks (CAC2) run against the harness
only: `terraform plan -detailed-exitcode` must exit 0 after the `import {}`
blocks apply.
